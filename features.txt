2. CONFIRMED BUSINESS DECISIONS
==================================================

These decisions are final. Do not ask me to choose alternatives.

A. BRANDING: PLATFORM-WIDE

Branding belongs to the entire ServiceFlow platform.

Requirements:
- Only authorized platform administrators can manage global branding.
- Organization owners and organization admins must not be able to modify platform branding.
- Branding must remain global, not organization-specific.
- Preserve existing branding functionality wherever possible.
- Prevent tenant users from modifying shared branding through direct URLs, Livewire actions, Filament actions, or other backend requests.
- Do not introduce organization-specific branding or unnecessary organization_id columns.
- Do not allow branding updates to modify the application's .env file.
- Store non-secret branding data using an appropriate persistent configuration/settings mechanism.
- Preserve existing branding uploads and validate their storage and access behavior.

B. SMTP: PLATFORM-WIDE ONLY

SMTP belongs to the ServiceFlow platform.

Requirements:
- Only platform administrators may access any platform mail administration interface.
- SMTP configuration must be managed through deployment environment variables and Laravel configuration.
- Do not support organization-specific SMTP configuration.
- Do not allow HTTP requests or Filament pages to write SMTP credentials into .env.
- Do not store SMTP passwords as plaintext in SystemSetting or another database table.
- Do not expose SMTP passwords or other secrets in forms, logs, API responses, debugging output, or frontend markup.
- Application code must consume configured mail settings through Laravel's configuration system.
- Avoid calling env() directly from application pages, resources, services, or other runtime code.
- Do not introduce an encrypted database-based SMTP settings system.
- If an SMTP settings UI currently exists, replace unsafe editing behavior with an appropriate read-only configuration/status interface or remove it if unnecessary.
- Clearly document how SMTP is configured during deployment.

C. DEMO SEEDER: DEVELOPMENT-ONLY

Demo accounts must never be created automatically in production.

Requirements:
- Separate essential application/reference data from demo-account provisioning.
- Demo accounts must only be provisioned in explicitly permitted local/development environments.
- Permit the testing environment where necessary for automated tests.
- Production and staging environments must not receive demo accounts.
- Protect against manually invoking the demo seeder in a forbidden environment.
- Do not rely only on hiding a button or changing documentation.
- Never use shared known demo passwords in production.
- Do not silently disable or delete existing seeder tests.
- Update the tests to verify the new security behavior.
- Preserve any required role or reference-data seeding that is genuinely needed outside development.

Do not assume all existing seeders are demo seeders. Inspect their responsibilities before changing DatabaseSeeder.

TASK 2 — SECURE GLOBAL BRANDING

Implement the confirmed platform-wide branding policy.

Acceptance criteria:
- Branding is global.
- Only platform administrators can update branding.
- Organization owners and organization admins cannot edit branding.
- Direct backend actions cannot bypass the restriction.
- Global branding changes cannot be initiated by a tenant user.
- No branding request writes to .env.
- Existing branding data is preserved.
- Existing branding functionality continues working for authorized platform administrators.

Review authorization at both page-access and action/save levels.

TASK 3 — SECURE SMTP CONFIGURATION

Refactor the existing SMTP administration implementation.

Acceptance criteria:
- SMTP remains platform-wide.
- SMTP configuration is deployment-managed.
- No application request writes SMTP credentials to .env.
- No plaintext SMTP secrets are stored in database settings.
- No organization can configure its own SMTP.
- Runtime application code uses Laravel config rather than direct env() calls.
- SMTP secrets are never displayed back to the browser.
- Platform administrators cannot accidentally expose credentials through a settings page.
- Document the environment variables and deployment procedure.

Do not break existing mail functionality unnecessarily.

TASK 4 — SECURE DEMO ACCOUNT SEEDING

Refactor demo-account provisioning.

Acceptance criteria:
- Demo accounts can be created in permitted local/development environments.
- Automated tests can still provision the accounts they need.
- Production and staging cannot create demo accounts through DatabaseSeeder or direct demo-seeder invocation.
- Production seeding of essential reference data remains possible where required.
- Existing seeder tests are updated to verify the intended behavior.
- README documentation no longer advertises production-unsafe default credentials.
- No production setup instructions recommend running a demo-account seeder.

Use the existing environment conventions in the project. Do not invent a separate environment-management system.

TASK 5 — FIX MEMBERSHIP / GLOBAL USER IDENTITY BOUNDARY

The audit identified that editing a membership can modify the globally shared User record.

A user may belong to multiple organizations.

Implement the following separation:

Membership-level operations may modify:
- Membership status
- Organization-specific roles
- Branch assignments
- Other organization-specific membership attributes already supported by the project

Tenant membership editing must not silently modify:
- Global user name
- Global user email
- Global password
- Global authentication credentials

If a global profile-editing workflow is needed, keep it separate from tenant membership administration and enforce appropriate authorization.

Acceptance criteria:
- An organization administrator cannot change a shared user's global email or password by editing their membership.
- An organization administrator cannot unintentionally change the user's global identity.
- Updating one membership does not alter another organization's membership.
- Existing membership role and branch assignment functionality continues working.
- Authorized account-profile operations remain separate.

Do not create duplicate User records for the same person merely to solve this problem.
